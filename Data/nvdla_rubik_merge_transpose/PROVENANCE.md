# nvdla_rubik_merge_transpose provenance

assembled: 2026-08-19

source: an earlier internal task package
        (copied out of; the source tree was not modified)

The real NVDLA RUBIK register-file core in MERGE mode at INT8 precision. The
formal top drives recurrent legal 32-atom batches of arbitrary 512-bit source
data into the core's 32 x 16-bit RAM bank set, then reads the batch back out
under symbolic downstream backpressure. An independent checker recomputes the
byte-matrix transpose from the accepted source atoms — without reusing the
RTL's shift, combine, recombine or RAM-address functions — and asserts output
presence, output mask and all 512 remapped data bits.

top: nvdla_rubik_merge_transpose_ft
environment: lists/diag_rubik_merge_transpose.tcl (task
`diag_rubik_merge_transpose`, declares NO assumption of its own — see below)
target: T_RUBIK_MERGE_TRANSPOSE
        (nvdla_rubik_merge_transpose_ft.u_checker.T_RUBIK_MERGE_TRANSPOSE)

Frozen configuration, from the source's `DERIVATION.json` and visible in the
formal top: `reg2dp_rubik_mode = 2'd2` (MERGE), `reg2dp_in_precision = 2'd0`
(INT8), 32 atoms per batch of 64 bytes each, `rf_rd_mask = 12'h820`, recurrent
batches (the sequencer returns to warm-up after the last output drains).

## What changed from the source's tcl/setup.tcl, and why

`elaborate -top nvdla_rubik_merge_transpose_ft -disable_auto_bbox`,
`set_clock_reference_mode auto`, `clock nvdla_core_clk`, `set_cumulative_reset

Note what is NOT there and is not an omission: no `+incdir+` and no
`+define+VLIB_BYPASS_POWER_CG`. The source's analyze line has neither. This
package ships no clock gate — the RUBIK core's only instantiated cell is the
RAM — and no include directory.

Dropped, with reasons — the same family as `nvdla_mcif_order`, whose
`PROVENANCE.md` gives them at length:

- **The name censuses** over `FLS_BASE_ASSERTIONS` + `FLS_HELPER_PROPERTIES`,
  `FLS_BASE_ASSUMPTIONS` and `FLS_BASE_COVERS`. `cex.tcl` runs `LABEL_INDEX`,
  `CHECK_FT_MODULES` and `CHECK_LABEL_COLLISIONS` instead.
- **`HELPER_RESOLUTION_FAIL`.** Same reason.
- **`MULTI_DRIVEN` as an error**, now the reported
  `MULTIPLE_DRIVEN count=... list=...`.
- **`+define+FLS_EVALUATION` and `+incdir+<submission>`.** See the scrub below.

This package's `fls_setup` has no `FROZEN_INPUT_MISSING` loop and no
`TARGET_RESOLUTION_FAIL` block — alone among the five — so there was nothing
there to drop. The target census is stated in the diag anyway, as a printed
count that fails only on zero, so this task's diag is the same shape as the
other four.

Added, not in the source: `AFRA_ELAB_EXTRA` handling (the payload exports it
unconditionally and a recipe that ignores it drops the run's elaborate switches
silently), `set_elab_time_limit`, `compilation -profile`, `task -create FPV`,
and the proofgrid profile load.

Deliberately NOT added: `-create_related_covers` / `-witness_cover_property`.
The source task elaborates without them, and they would attach
precondition/witness covers to every helper an agent writes, changing what the
cover phase counts.

## Scrubbed

- `ft/nvdla_rubik_merge_transpose_ft.sv`, 3 lines deleted at the end of the
  module:

        `ifdef FLS_EVALUATION
        `include "helpers.sv"
        `endif

  Not a leak — an incompatibility, the same one recorded for the other four
  packages. In the source flow a submission is one `helpers.sv` textually
  included INSIDE the top module; v5 stages one bound standalone file per worker
  and `v5/elab.tcl` fails a worker whose file does not bind under its own module
  name. Left in, the directive is either inert (no `FLS_EVALUATION`) or fatal
  (no such file), and it would tell an agent to write in a shape the harness
  rejects. The `placement` string for this task must be the standalone/`bind`
  default.

Nothing else was removed. The checker's comment on `A_READY_RESERVATION` states
what the assumption means, which is the environment's own statement, and the
formal top's `PH_*` localparams are its own sequencer. Neither points at a
proof.

## Covers

The source's `DERIVATION.json` lists 5 covers, all in the checker and all

`C_RESERVED_OUTPUT`, `C_TWO_BATCHES`. They are what `COVER_DEPTH` will count if

## Assumptions: 1, and not from the diag

`A_READY_RESERVATION` — `read_pop |=> dma_wr_data_rdy`, the consumer's promise
not to withdraw a ready reservation between the synchronous RAM read launch and
its output cycle. It is written in the checker and so is already elaborated by
`tc_elab.tcl`. `diag_rubik_merge_transpose` adds nothing, so
`diagnostic_assumption_count` prints 0 and that is correct; the diag prints a
second `package_assumption_count` line showing the 1.

Checked by reading `tcl/setup.tcl` and `tcl/evaluate.tcl`: neither contains
`assume -from_assert`, so this task has no `PACKAGE_SWALLOWS` entry and
`PACKAGE_ASSUMED_HELPERS` is 0.

## DESIGN_KEEP: two patterns, and the FT is in one of them

This is the only one of the five nvdla packages whose formal top holds state,
and that state has to survive the reset cut. `taskdef.json` carries

    u_checker\.(expected_q|expected_index_q|pending_q|completed_batches_q)
    (phase_q|warmup_q|write_index_q|read_index_q|write_data_q)

both matched unanchored against instance paths as `get_design_info -list
register` returns them. The second pattern is deliberately written without a
hierarchical prefix: the five names it lists exist only in the formal top —
checked by grep, the RUBIK core declares no `_q`-suffixed identifier at all —
so the bare form matches whether or not Jasper prefixes the top module's name,
and cannot reach into the design.

Why each:

- `expected_q`, `expected_index_q`, `pending_q` — read directly by
  `T_RUBIK_MERGE_TRANSPOSE`. Cut, the target compares the design's output
  against an arbitrary expectation and fails at cycle 0 for a reason nothing in
  the design can correct.
- `completed_batches_q` — read by `C_TWO_BATCHES` and by nothing else. Cut,
  that cover is reachable at cycle 0 for free and `COVER_DEPTH` measures
  nothing. It costs 2 bits.
- `phase_q`, `warmup_q`, `write_index_q`, `read_index_q`, `write_data_q` — the
  formal top's stimulus sequencer. This is not a convenience. The sequencer is
  what orders a full 32-atom write batch ahead of any read, and that ordering is
  the only thing that makes the comparison well-posed: both the RUBIK RAM bank
  and the checker's `batch` array are unreset storage, so if a read can precede
  the writes, the design returns one arbitrary value and the checker expects a
  different arbitrary value and no helper can close the gap. Cut, the task is
  not merely harder, it is false. Kept, `phase_q` starts at `PH_WARMUP` and
  every read is preceded by the 32 writes that filled both.

`batch` is deliberately NOT in the pattern, on the same argument as pmesh's
`ref_mem`. The checker's reset branch assigns only the four `*_q` registers;
`batch` is written only on a `write_fire`, so it has no reset value at all, and
`stopat -reset` cuts a reset value. Keeping a register that has none is a no-op
and would only inflate the `KEEP_PATTERN design` count in the round log, which
is read as a measurement.

The caveat that travels with a result from this task is therefore sharper than
pmesh's. "A read entry was written" does not hold by construction here, and it
does not hold from the checker alone either: it holds because `phase_q` is
anchored at reset and the sequencer is a straight-line WARMUP -> WRITE(32) ->
READ(32) -> DRAIN loop. Anyone changing the keep set must keep the sequencer, or
the number the task produces is not about RUBIK.

All nine kept names are reset-assigned, so neither pattern can match zero and
neither can trip `cex.tcl`'s "design keep pattern matched nothing" FAIL.

Everything else stays cut: the RUBIK core's 32 RAM instances, its read pipeline
(`rf_rd_pop_d`, `rf_rd_oaddr_d`, `rd_data_raw_reg`), its write and read control
and its output registers.

## The v4 target-label blocker no longer applies

The two tasks ported on 2026-08-12 recorded a blocker: `v5/round.py` emitted
`set target_labels` from `v4pre_round.TARGETS`, the hardcoded the internal reference task pair,
so a ported task resolved no target and `cex.tcl` aborted with `no target
property resolved`. That has since been fixed — `v5/round.py:287` now reads
`taskdefs.TASKS[self.task]["target_labels"]`, and this package supplies that
key through `taskdef.json`. `v4pre_round.TARGETS` still holds the internal reference task
pair, which is correct for the v4 path and does not reach v5.

`cex.tcl:LABEL_INDEX` keys on the last dot-separated component of a property
name, so the bare label in `target_labels` is the right form.
