# nvdla_cdp_syncfifo_order provenance

assembled: 2026-08-19

source: an earlier internal task package
        (copied out of; the source tree was not modified)

The real NVDLA CDP synchronization FIFO carries three stateful streams: a
paired CVT data/info pair that enters together and drains independently through
the `mul` and `ocvt` outputs, and a separate SUM stream draining through `itp`.
Symbolic input traffic and three independent symbolic output backpressures
drive the unmodified 80/80/60-entry FIFO control. An independent set of
reference queues asserts that each output presents the oldest unconsumed entry
of its stream, over all 72 data bits, all 15 info bits and all 168 SUM bits.

top: nvdla_cdp_syncfifo_order_ft
environment: lists/diag_cdp_syncfifo_order.tcl (task `diag_cdp_syncfifo_order`,
NO assumptions — see below)
target: T_SYNCFIFO_DATA_ORDER
        (nvdla_cdp_syncfifo_order_ft.u_checker.T_SYNCFIFO_DATA_ORDER)

Frozen configuration, from the source's `DERIVATION.json`: real FIFO depths 80
(CVT data), 80 (CVT info) and 60 (SUM); widths 72 / 15 / 168; reference depths
128 for the CVT pair and 64 for SUM, chosen to exceed the real FIFO plus its
input elastic stage so the reference model never constrains traffic.

## What changed from the source's tcl/setup.tcl, and why

Kept: `clear -all`, the analyze set and its order, `+define+SYNTHESIS`,
`+define+VLIB_BYPASS_POWER_CG`, `+incdir+include`, `elaborate -top
nvdla_cdp_syncfifo_order_ft -disable_auto_bbox`, `set_clock_reference_mode
auto`, `clock nvdla_core_clk`, `set_cumulative_reset on`, `reset -expression
{nvdla_core_rstn == 1'b0} -max_iterations 100`.

Dropped, with reasons — the same five as `nvdla_mcif_order`, whose
`PROVENANCE.md` gives them at length:

- **`FROZEN_INPUT_MISSING`**, which requires `<eval>/submission/helpers.sv`.
- **The name censuses** over `FLS_BASE_ASSERTIONS` + `FLS_HELPER_PROPERTIES`,
  `FLS_BASE_ASSUMPTIONS` and `FLS_BASE_COVERS`. This package's cover census is
  the strict `fls_require_exact_names` variant, extended with one
  `<assume>:precondition1` per base assumption — of which there are none here,
  so it reduces to "the elaborated cover set is exactly the 7 authored covers".
  Every helper an agent writes with an implication antecedent would add a
  precondition cover and fail it. `cex.tcl` runs `LABEL_INDEX`,
  `CHECK_FT_MODULES` and `CHECK_LABEL_COLLISIONS` instead.
- **`TARGET_RESOLUTION_FAIL` / `HELPER_RESOLUTION_FAIL`.** The target census
  survives in the diag as a printed count that fails only on zero.
- **`MULTI_DRIVEN` as an error**, now the reported
  `MULTIPLE_DRIVEN count=... list=...`.
- **`+define+FLS_EVALUATION` and `+incdir+<submission>`.** See the scrub below.

Added, not in the source: `AFRA_ELAB_EXTRA` handling (the payload exports it
unconditionally and a recipe that ignores it drops the run's elaborate switches
silently), `set_elab_time_limit`, `compilation -profile`, `task -create FPV`,
and the proofgrid profile load.

Deliberately NOT added: `-create_related_covers` / `-witness_cover_property`.
The source task elaborates without them, and they would attach
precondition/witness covers to every helper an agent writes, changing what the
cover phase counts.

## Scrubbed

- `ft/nvdla_cdp_syncfifo_order_ft.sv`, 3 lines deleted at the end of the module:

        `ifdef FLS_EVALUATION
        `include "helpers.sv"
        `endif

  Not a leak — an incompatibility, the same one recorded for
  `openpiton_pmesh_order`, `nvdla_mcif_order` and `nvdla_bdma_data_order`. In
  the source flow a submission is one `helpers.sv` textually included INSIDE the
  top module; v5 stages one bound standalone file per worker and `v5/elab.tcl`
  fails a worker whose file does not bind under its own module name. Left in,
  the directive is either inert (no `FLS_EVALUATION`) or fatal (no such file),
  and it would tell an agent to write in a shape the harness rejects. The
  `placement` string for this task must be the standalone/`bind` default.

Nothing else was removed. The formal top's and the checker's header comments
state what was built — three streams, the CVT pair entering together and
draining independently — which is the task's own statement of its scope, not a
hint at a proof. The checker's remark that the reference capacities exceed the
real FIFO plus its input stage is likewise a statement of the model's own
sizing, and the sizes are readable from the array declarations two lines below
it in any case.

## DESIGN_KEEP

Non-empty, for the same reason as the other ordering tasks: the target's
instrument is registered. `T_SYNCFIFO_DATA_ORDER` reads `data_count`,
`info_count`, `sum_count`, `data_rptr`, `info_rptr`, `sum_rptr` and the three
reference arrays. Under `ENTER_FRA_KEEP` every register not matched by a keep
pattern starts arbitrary, so with an empty keep list the reference queues start
arbitrary and the target is falsified at cycle 0 for a reason that is not the
design's and that nothing in the design can correct.

The pattern in `taskdef.json` is

    u_checker\.(cvt_wptr|data_rptr|info_rptr|data_count|info_count|sum_wptr|sum_rptr|sum_count|cvt_accepts|sum_accepts|mul_outputs|ocvt_outputs|itp_outputs|(mul|ocvt|itp)_stall_seen)

matched unanchored against instance paths as `get_design_info -list register`
returns them. It is the checker instance and nothing else: the real FIFO write
and read pointers, its occupancy counters, its output registers and the RAM
models all stay cut.

Two families, two reasons:

- `cvt_wptr`, `data_rptr`, `info_rptr`, `data_count`, `info_count`, `sum_wptr`,
  `sum_rptr`, `sum_count` — read by the target, directly or as the address of a
  reference array. `cvt_wptr` is not read by the target but is the write pointer
  the counts are honest about; cut, an entry could be read before it was
  written.
- `cvt_accepts`, `sum_accepts`, `mul_outputs`, `ocvt_outputs`, `itp_outputs`,
  `mul_stall_seen`, `ocvt_stall_seen`, `itp_stall_seen` — read by
  `C_CVT_FULL_WRAP`, `C_SUM_FULL_WRAP` and `C_ALL_OUTPUTS_AFTER_STALL` and by
  nothing else. Cut, those three covers are reachable at cycle 0 for free and
  `COVER_DEPTH` measures nothing. They cost 43 bits.

`data_ref`, `info_ref` and `sum_ref` are deliberately NOT in the pattern, on the
same argument as pmesh's `ref_mem`. The checker's reset branch assigns only the
pointer, count and census registers; the three arrays are written only on an
accepted input, so they have no reset value at all, and `stopat -reset` cuts a
reset value. Keeping a register that has none is a no-op and would only inflate
the `KEEP_PATTERN design` count in the round log, which is read as a
measurement.

The same caveat as pmesh applies and should travel with any result from this
task: "a read entry was written" holds by an argument, not by construction. Each
clause requires its count to be non-zero, and a count only becomes non-zero on
the accepted input that writes the array at the write pointer, so an entry is
never read before it is written — **provided the pointers start at reset**,
which is what the keep set buys. The arbitrary initial contents of the three
arrays (128 x 72 + 128 x 15 + 64 x 168 = 21888 bits) are unobservable only
because the pointer state is anchored.

All kept families are reset-assigned, so the pattern cannot match zero and
cannot trip `cex.tcl`'s "design keep pattern matched nothing" FAIL.

The formal top holds no register — every declaration in
`ft/nvdla_cdp_syncfifo_order_ft.sv` is a `wire` — so there is nothing on the FT
side to keep or to cut.

## The v4 target-label blocker no longer applies

The two tasks ported on 2026-08-12 recorded a blocker: `v5/round.py` emitted
`set target_labels` from `v4pre_round.TARGETS`, the hardcoded the internal reference task pair,
so a ported task resolved no target and `cex.tcl` aborted with `no target
property resolved`. That has since been fixed — `v5/round.py:287` now reads
`taskdefs.TASKS[self.task]["target_labels"]`, and this package supplies that
key through `taskdef.json`. `v4pre_round.TARGETS` still holds the internal reference task
pair, which is correct for the v4 path and does not reach v5.

`cex.tcl:LABEL_INDEX` keys on the last dot-separated component of a property
name, so the bare label in `target_labels` is the right form.
