# openpiton_pmesh_order provenance

assembled: 2026-08-13 (work item W6 of plans/0812-nightly.md)

source: an earlier internal task package
        (copied out of; the source tree was not modified)

Four independent single-flit streams converge through a real 3x3 OpenPiton
P-Mesh at `+define+PMESH_X_TILES=3 +define+PMESH_Y_TILES=3`, and an
independent four-queue reference oracle asserts per-flow FIFO order at the one
shared destination endpoint. The router RTL is upstream OpenPiton; the mesh
wrapper, the formal top and the oracle are task-authored.

top: openpiton_pmesh_order_scaled_ft
environment: lists/diag_pmesh_order.tcl  (task `diag_pmesh_order`, NO assumptions)
target: T_ORDER  (openpiton_pmesh_order_scaled_ft.u_checker.T_ORDER)

The source `DERIVATION.json` also lists 12 covers (`C_FLOW{0..3}_INJECT`,
`C_FLOW{0..3}_DELIVER`, `C_ALL_BACKLOG`, `C_UPSTREAM_CONTEND`,
`C_DOWNSTREAM_CONTEND`, `C_FOUR_FLOW_DELIVERY`). They elaborate with the
package and are what `COVER_DEPTH` will count if a round is given
`--cover-s`. They are not targets.

## What changed from the source's tcl/setup.tcl, and why

The source's `fls_setup` is a single-shot evaluator for one frozen submission.
Kept: `clear -all`, the analyze set, `+incdir+rtl/openpiton_dn`, the two
`PMESH_*_TILES` defines, `elaborate -top openpiton_pmesh_order_scaled_ft
-disable_auto_bbox`, `set_clock_reference_mode auto`, `clock clk`,
`set_cumulative_reset on`, `reset -expression {reset_n == 1'b0}
-max_iterations 100`.

Dropped, with reasons:

- **The name censuses** (`fls_require_exact_names` over
  `FLS_BASE_ASSERTIONS` + `FLS_HELPER_PROPERTIES`, and the assumption census).
  They demand the elaborated property set equal a list computed by a Python
  front end that v5 does not run. v5 stages a different helper set every round,
  so an exact-match census rejects every legal round. Not lost: `cex.tcl` runs
  `LABEL_INDEX`, `CHECK_FT_MODULES` and `CHECK_LABEL_COLLISIONS` after this file.
- **`TARGET_RESOLUTION_FAIL` / `HELPER_RESOLUTION_FAIL`.** Same reason. The
  target census survives in the diag as a printed count that fails only on zero.
- **`MULTI_DRIVEN` as an error.** Now reported as
  `MULTIPLE_DRIVEN count=... list=...`. An abort here kills the round before
  any verdict; the number in the log answers the same question.
- **`+define+FLS_EVALUATION` and `+incdir+<submission>`.** See the scrub below.
- **Two analyze calls (`-v2k` for the router, `-sv12` for the rest) became one
  `-sv12`.** v5 appends each worker's file to ONE list, so the package needs one
  appendable list. Checked before deciding: with comments stripped, the 21
  Verilog-2001 files declare no identifier that SystemVerilog-2012 reserves.
- **`fls_configure_proofgrid`, the whole of `tcl/evaluate.tcl`.** That is the
  source's own LSF/proofgrid policy, its property ledger and its
  `o_build`-queue and job-prefix gates. v5 brings its own (`v5/grid.tcl`,
  `CONFIG_GRID`) and writes its own report. `tcl/` was not copied at all.

Added, not in the source: `AFRA_ELAB_EXTRA` handling (the payload exports it
unconditionally and a recipe that ignores it drops the run's elaborate switches
silently), `set_elab_time_limit`, `compilation -profile`, `task -create FPV`,
and the proofgrid profile load.

Deliberately NOT added: `-create_related_covers` / `-witness_cover_property`,
which the internal reference task recipe uses. The source task elaborates without them, and
they would attach precondition/witness covers to every helper an agent writes,
changing what the cover phase counts.

## Scrubbed

This package is copied into every agent workspace, so anything in it that
describes a solution or a golden environment would make the run not blind.

- `ft/openpiton_pmesh_order_scaled_ft.sv`, 3 lines deleted at the end of the
  module:

        `ifdef FLS_EVALUATION
        `include "helpers.sv"
        `endif

  Not a leak -- an incompatibility. In the source flow a submission is one
  `helpers.sv` textually included INSIDE the top module. v5 stages one bound
  standalone file per worker and `v5/elab.tcl` fails a worker whose file does
  not bind under its own module name. Left in, the directive is either inert
  (no `FLS_EVALUATION`) or fatal (no such file), and it would tell an agent to
  write in a shape the harness rejects. This is why the `placement` string for
  this task must be the standalone/`bind` one, not the include one that
  `ordering_core_scaled_v2` uses.
- `rtl/pmesh_top.v`, 4 comment hunks: references to the **VC-deadlock FV
  proof** this fabric was first packaged for, and to a golden FV environment
  that is not in this package -- the bound `fv_pmesh` harness, `FV_pmesh.sv`,
  `FV_pmesh_assumes`, `FV_pmesh_endpoint_model`, and an internal FV model
  comparison. Two harms, no benefit: it names a verification environment an
  agent could go looking for, and it points at a different property (VC
  deadlock, "NoC3 never blocked by NoC1/2") than the one being proved here.
  A confidently wrong hint is worse than none. Code untouched.

Kept deliberately, with the reasoning, so the next reader does not have to
re-derive it:

- The formal top's header comment (the four flows, their tile coordinates and
  their XY routes) and the `SRC0..SRC3`/`DST` localparams. This is the task's
  own statement of what was built, the same role the internal reference task's
  `Cell: a=2 srcs, b=2 dsts, e=4 entries` line plays. The routes are recoverable
  from the localparams three lines below in any case.
- `upstream_contention` / `downstream_contention` and their comment. These are
  load-bearing code: they feed `C_UPSTREAM_CONTEND` and `C_DOWNSTREAM_CONTEND`
  and reference the two south-output arbiters by hierarchical name. Deleting
  the comment while the code stays buys nothing.

## DESIGN_KEEP: this task NEEDS a non-empty one

Unlike the other task ported tonight, `DESIGN_KEEP` for this task must NOT be
an empty list.

The target's instrument is registered. `sva/..._checker.sv` maintains a
128-entry reference queue per flow -- `ref_mem`, `ref_wr_ptr`, `ref_rd_ptr`,
`ref_count`, all `always @(posedge clk)` -- and `T_ORDER` reads all of it
through `target_ok`. Under `ENTER_FRA_KEEP` every register not matched by a
keep pattern starts arbitrary. With an empty keep list the reference queue
starts arbitrary, `selected_match` is garbage, and `T_ORDER` is falsified at
cycle 0 for a reason that is not the design's and that nothing in the design
can correct. That is the same "preserve the instrument, cut the design" rule
`_CHECKER_KEEP` follows for the internal reference task's an internal register family registers.

The pattern reported for `taskdefs.DESIGN_KEEP` is

    r"u_checker\.ref_(wr_ptr|rd_ptr|count)"

matched unanchored against instance paths as `get_design_info -list register`
returns them, which is the form `_CHECKER_KEEP` uses. It is the checker
instance and nothing else: the fabric, the endpoint credit counters and the
formal top's own `dut_ready` all stay cut.

### The oracle's storage is unreset, and the keep set is its pointers only

This is a fact about the task, not a configuration preference, and it changes
how the results should be read.

`ref_mem` is deliberately NOT in the pattern. The checker's reset branch
assigns `ref_wr_ptr`, `ref_rd_ptr` and `ref_count` and nothing else; `ref_mem`
is written only in the `else` branch, on an injection. So `ref_mem` has no
reset value at all, and `stopat -reset` cuts a reset value. Keeping a register
that has none is a no-op: those 4 x 128 x 64 = 32768 bits start arbitrary
whether or not a pattern matches them. Including them would buy nothing and
would inflate the `KEEP_PATTERN design` count in the round log, which is read
as a measurement.

So the kept state is exactly

    ref_wr_ptr   4 x 7 bits
    ref_rd_ptr   4 x 7 bits
    ref_count    4 x 8 bits     = 88 bits

and the instrument is anchored at its POINTERS, not at its memory.

That is enough for `T_ORDER` to mean what it says, but by an argument rather
than by construction. `selected_match` requires `ref_count[dst_flow] != 0`,
and a count only becomes non-zero through an injection, which is the same
event that writes `ref_mem` at `ref_wr_ptr`. So an entry is never read before
it has been written -- **provided the pointers start at reset**, which is what
the keep set buys. "A read entry was written" is therefore a property that has
to hold, not something the keep set establishes. Anyone reading a pmesh result
later needs to know that distinction: the arbitrary initial contents of
`ref_mem` are unobservable only because the pointer state is anchored and the
count is honest about how many entries have been written.

`dut_ready` (formal top) is left cut deliberately. It gates
`checker_reset_n`; arbitrary-1 is the normal case and arbitrary-0 merely holds
the oracle in reset for one cycle with `T_ORDER` disabled by its own
`disable iff`. Neither produces a spurious counterexample.

All three kept families are reset-assigned, so the pattern cannot match zero
and cannot trip `cex.tcl`'s "design keep pattern matched nothing" FAIL. Expect
12 hits if Jasper lists array elements individually, 3 if it lists arrays.

## Harness dependency -- was a blocker, now satisfied

When this package was assembled, `v5/round.py` emitted
`set target_labels {tcl_list(v4pre_round.TARGETS)}` -- the hardcoded the internal reference task
pair -- so a pmesh round resolved no target and `cex.tcl` aborted with `no
target property resolved`. The model phase was unaffected, going through
`derive_targets`, which was always per-task.

**Fixed.** `v5/round.py:287` now reads
`taskdefs.TASKS[self.task]["target_labels"]`, and `v6_dataset/round.py:303`
additionally accepts a per-run override so the phase-1 screen can prove a list
of authored candidates without touching this file. `v4pre_round.TARGETS` still
exists and is still the internal reference task pair; it is the v4 path's and is no longer
read here.

`cex.tcl:LABEL_INDEX` keys on the last dot-separated component, so `["T_ORDER"]`
resolves. Corrected 2026-08-19 -- `tasks/l15_l2_mshr_onehot/PROVENANCE.md`
already carried the correction and this file did not.
