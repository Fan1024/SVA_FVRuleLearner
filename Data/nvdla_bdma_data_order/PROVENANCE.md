# nvdla_bdma_data_order provenance

assembled: 2026-08-19

source: an earlier internal task package
        (copied out of; the source tree was not modified)

The real NVDLA BDMA MCIF-to-MCIF path — the load engine, the 20-entry
command-context queue and the store engine with its latency FIFO — copies a
fixed two-line, eight-beat-per-line command. Accepted MCIF read responses are
the reference stream; an independent 64-entry queue asserts that every accepted
MCIF write-data packet consumes that stream in the same order. Command arrival,
memory backpressure and response data stay symbolic.

top: nvdla_bdma_data_order_ft
environment: lists/diag_bdma_data_order.tcl (task `diag_bdma_data_order`,
declares NO assumption of its own — see below)
target: T_DATA_ORDER  (nvdla_bdma_data_order_ft.u_checker.T_DATA_ORDER)

Frozen configuration, from the source's `DERIVATION.json` and visible in the
formal top: `REF_DEPTH=64`, `reg2dp_line_size=15` (a 16-atom / eight-beat
line), `reg2dp_line_repeat_number=1` (two lines), `reg2dp_surf_repeat_number=0`
(one surface), source and destination RAM type both MCIF. The CVIF side is tied
off: `bdma2cvif_*_ready` held high, `cvif2bdma_rd_rsp_valid` held low.

## What changed from the source's tcl/setup.tcl, and why

Kept: `clear -all`, the analyze set and its order, `+define+SYNTHESIS`,
`+define+VLIB_BYPASS_POWER_CG`, `+incdir+include`, `elaborate -top
nvdla_bdma_data_order_ft -disable_auto_bbox`, `set_clock_reference_mode auto`,
`clock nvdla_core_clk`, `set_cumulative_reset on`, `reset -expression
{nvdla_core_rstn == 1'b0} -max_iterations 100`.

Dropped, with reasons — the same five as `nvdla_mcif_order`, whose
`PROVENANCE.md` gives them at length:

- **`FROZEN_INPUT_MISSING`**, which requires `<eval>/submission/helpers.sv`.
- **The name censuses** over `FLS_BASE_ASSERTIONS` + `FLS_HELPER_PROPERTIES`,
  `FLS_BASE_ASSUMPTIONS` and `FLS_BASE_COVERS`. `cex.tcl` runs `LABEL_INDEX`,
  `CHECK_FT_MODULES` and `CHECK_LABEL_COLLISIONS` instead.
- **`TARGET_RESOLUTION_FAIL` / `HELPER_RESOLUTION_FAIL`.** The target census
  survives in the diag as a printed count that fails only on zero.
- **`MULTI_DRIVEN` as an error**, now the reported
  `MULTIPLE_DRIVEN count=... list=...`.
- **`+define+FLS_EVALUATION` and `+incdir+<submission>`.** See the scrub below.

One ordering difference, and it is only an ordering difference: the source's
`analyze` lists `NV_NVDLA_BDMA_cq.v` before `nvdla_bdma_formal_ram.sv`, its own
`FROZEN_INPUT_MISSING` list has them the other way round, and `lists/`
groups the RAM model with the library cells. Under `--single-unit` / one
`analyze` the order of module declarations does not change elaboration.

Added, not in the source: `AFRA_ELAB_EXTRA` handling (the payload exports it
unconditionally and a recipe that ignores it drops the run's elaborate switches
silently), `set_elab_time_limit`, `compilation -profile`, `task -create FPV`,
and the proofgrid profile load.

Deliberately NOT added: `-create_related_covers` / `-witness_cover_property`.
The source task elaborates without them, and they would attach
precondition/witness covers to every helper an agent writes, changing what the
cover phase counts.

## Scrubbed

- `ft/nvdla_bdma_data_order_ft.sv`, 4 lines deleted at the end of the module (a
  blank line and the three directives):

        `ifdef FLS_EVALUATION
        `include "helpers.sv"
        `endif

  Not a leak — an incompatibility, the same one recorded for
  `openpiton_pmesh_order` and `nvdla_mcif_order`. In the source flow a
  submission is one `helpers.sv` textually included INSIDE the top module; v5
  stages one bound standalone file per worker and `v5/elab.tcl` fails a worker
  whose file does not bind under its own module name. Left in, the directive is
  either inert (no `FLS_EVALUATION`) or fatal (no such file), and it would tell
  an agent to write in a shape the harness rejects. The `placement` string for
  this task must be the standalone/`bind` default.

Nothing else was removed. The formal top's and the checker's header comments
state what was built — the fixed command shape and which interfaces the oracle
watches — which is the task's own statement of its scope, not a hint at a proof.

## Assumptions: 5, and none of them from the diag

All five are written in the checker and are already elaborated by
`tc_elab.tcl`:

    A_CMD_HOLD           sticky command valid
    A_RSP_HOLD           sticky response valid and payload
    A_RSP_HAS_REQUEST    no response beat without an outstanding read
    A_READ_WINDOW        read requests stall above 56 outstanding beats
    A_REFERENCE_WINDOW   no response accepted into a full reference queue

`diag_bdma_data_order` adds nothing, so `diagnostic_assumption_count` prints 0
and that is correct. The diag prints a second `package_assumption_count` line so
a reader of the round log can see the 5 without opening the source.

Note that `A_RSP_HAS_REQUEST`, `A_READ_WINDOW` and `A_REFERENCE_WINDOW` are all
stated over the checker's own registers, which is why those registers are in the
keep set below.

Checked by reading `tcl/setup.tcl` and `tcl/evaluate.tcl`: neither contains
`assume -from_assert`, so this task has no `PACKAGE_SWALLOWS` entry and
`PACKAGE_ASSUMED_HELPERS` is 0.

## DESIGN_KEEP

Non-empty, for the same reason as `openpiton_pmesh_order` and
`nvdla_mcif_order`: the target's instrument is registered. `T_DATA_ORDER` reads
`ref_count`, `ref_rd_ptr` and `ref_mem`, all `always @(posedge clk or negedge
reset_n)`. Under `ENTER_FRA_KEEP` every register not matched by a keep pattern
starts arbitrary, so with an empty keep list the reference queue starts
arbitrary and `T_DATA_ORDER` is falsified at cycle 0 for a reason that is not
the design's and that nothing in the design can correct.

The pattern in `taskdef.json` is

    u_checker\.(outstanding_beats|ref_count|ref_wr_ptr|ref_rd_ptr|commands_seen)

matched unanchored against instance paths as `get_design_info -list register`
returns them. It is the checker instance and nothing else: the BDMA load
sequencer, the context queue, the store engine and the latency FIFO all stay
cut.

Three families, three reasons:

- `ref_count`, `ref_rd_ptr`, `ref_wr_ptr` — read by the target, directly or as
  the address of `ref_mem`.
- `outstanding_beats` — read by the assumptions `A_RSP_HAS_REQUEST` and
  `A_READ_WINDOW`. Cut, the memory environment is stated against an arbitrary
  ledger, which is not the environment the task is stated in.
- `commands_seen` — read by the cover `C_TWO_COMMANDS` and by nothing else.
  Cut, that cover is reachable at cycle 0 for free and `COVER_DEPTH` measures
  nothing. It costs 3 bits.

`ref_mem` is deliberately NOT in the pattern, exactly as in pmesh and mcif. The
checker's reset branch assigns only the five families above; `ref_mem` is
written only on an accepted read response, so it has no reset value at all, and
`stopat -reset` cuts a reset value. Keeping a register that has none is a no-op
and would only inflate the `KEEP_PATTERN design` count in the round log, which
is read as a measurement.

So the same caveat pmesh carries applies here and should travel with any result
from this task: "a read entry was written" holds by an argument, not by
construction. The target requires `ref_count != 0`, and the count only becomes
non-zero on the accepted response that writes `ref_mem` at `ref_wr_ptr`, so an
entry is never read before it is written — **provided the pointers start at
reset**, which is what the keep set buys. The arbitrary initial contents of
`ref_mem` (64 x 512 = 32768 bits) are unobservable only because the pointer
state is anchored.

All five kept families are reset-assigned, so the pattern cannot match zero and
cannot trip `cex.tcl`'s "design keep pattern matched nothing" FAIL.

The formal top holds no register — every declaration in
`ft/nvdla_bdma_data_order_ft.sv` is a `wire` — so there is nothing on the FT
side to keep or to cut.

## The v4 target-label blocker no longer applies

The two tasks ported on 2026-08-12 recorded a blocker: `v5/round.py` emitted
`set target_labels` from `v4pre_round.TARGETS`, the hardcoded the internal reference task pair,
so a ported task resolved no target and `cex.tcl` aborted with `no target
property resolved`. That has since been fixed — `v5/round.py:287` now reads
`taskdefs.TASKS[self.task]["target_labels"]`, and this package supplies that
key through `taskdef.json`. `v4pre_round.TARGETS` still holds the internal reference task
pair, which is correct for the v4 path and does not reach v5.

`cex.tcl:LABEL_INDEX` keys on the last dot-separated component of a property
name, so the bare label in `target_labels` is the right form.
