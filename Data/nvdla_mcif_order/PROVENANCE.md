# nvdla_mcif_order provenance

assembled: 2026-08-19

source: an earlier internal task package
        (copied out of; the source tree was not modified)

Four real generated NVDLA clients (BDMA, SDP, PDP, CDP) drive the unmodified
MCIF read path — request BPT/SPT/CVT expansion, the weighted round-robin
arbiter, the context queue and the response egress — out to one public AXI read
port. An independent per-client reference FIFO, watching only the public AXI
and client interfaces, asserts that every client response carries the oldest
unconsumed AXI beat for that client, plus issue shape, ownership and an
end-to-end outstanding conservation equation.

top: nvdla_mcif_order_ft
environment: lists/diag_mcif_order.tcl (task `diag_mcif_order`, declares NO
assumption of its own — see below)
target: T_MCIF_ORDER  (nvdla_mcif_order_ft.u_checker.T_MCIF_ORDER)

Frozen configuration, from the source's `DERIVATION.json` and visible in the
formal top: `NCLIENT=4`, `REF_DEPTH=64`, `reg2dp_rd_os_cnt=15` (a 16-beat
outstanding window), active AXI IDs 0..3, equal nonzero weights on the four
active clients and zero weight on the six tied-off ones.

## What changed from the source's tcl/setup.tcl, and why

Kept: `clear -all`, the analyze set and its order, `+define+SYNTHESIS`,
`+define+VLIB_BYPASS_POWER_CG`, `+incdir+include`, `elaborate -top
nvdla_mcif_order_ft -disable_auto_bbox`, `set_clock_reference_mode auto`,
`clock nvdla_core_clk`, `set_cumulative_reset on`, `reset -expression
{nvdla_core_rstn == 1'b0} -max_iterations 100`.

Dropped, with reasons:

- **`FROZEN_INPUT_MISSING`.** It requires `<eval>/submission/helpers.sv` to
  exist. v5 stages one bound standalone file per worker under a worker name;
  there is no `helpers.sv` and the check would fail every round.
- **The name censuses** (`fls_require_exact_names` over
  `FLS_BASE_ASSERTIONS` + `FLS_HELPER_PROPERTIES`, over `FLS_BASE_ASSUMPTIONS`,
  and `fls_require_names_present` over `FLS_BASE_COVERS`). They demand the
  elaborated property set equal a list computed by a Python front end that v5
  does not run, and v5 stages a different helper set every round. Not lost:
  `cex.tcl` runs `LABEL_INDEX`, `CHECK_FT_MODULES` and
  `CHECK_LABEL_COLLISIONS` after this file.
- **`TARGET_RESOLUTION_FAIL` / `HELPER_RESOLUTION_FAIL`.** Same reason. The
  target census survives in the diag as a printed count that fails only on zero.
- **`MULTI_DRIVEN` as an error.** Now reported as
  `MULTIPLE_DRIVEN count=... list=...`. An abort here kills the round before
  any verdict; the number in the log answers the same question.
- **`+define+FLS_EVALUATION` and `+incdir+<submission>`.** See the scrub below.

Added, not in the source: `AFRA_ELAB_EXTRA` handling (the payload exports it
unconditionally and a recipe that ignores it drops the run's elaborate switches
silently), `set_elab_time_limit`, `compilation -profile`, `task -create FPV`,
and the proofgrid profile load.

Deliberately NOT added: `-create_related_covers` / `-witness_cover_property`.
The source task elaborates without them, and they would attach
precondition/witness covers to every helper an agent writes, changing what the
cover phase counts.

## Scrubbed

This package is copied into every agent workspace, so anything in it that
describes a solution or a golden environment would make the run not blind.

- `ft/nvdla_mcif_order_ft.sv`, 5 lines deleted at the end of the module (a
  blank line, a comment and the three directives):

        // Evaluator-only helper hook.  It is absent from bare elaboration.
        `ifdef FLS_EVALUATION
        `include "helpers.sv"
        `endif

  Not a leak — an incompatibility, the same one recorded for
  `openpiton_pmesh_order`. In the source flow a submission is one `helpers.sv`
  textually included INSIDE the top module. v5 stages one bound standalone file
  per worker and `v5/elab.tcl` fails a worker whose file does not bind under its
  own module name. Left in, the directive is either inert (no `FLS_EVALUATION`)
  or fatal (no such file), and it would tell an agent to write in a shape the
  harness rejects. The `placement` string for this task must therefore be the
  standalone/`bind` default, not the include one `ordering_core_scaled_v2` uses.

Nothing else was removed. The checker's and the formal top's comments state
what was built — the four active clients, the tied-off six, the frozen weights
and window, and which endpoint signals the conservation clause needs — which is
the task's own statement of its scope, not a hint at a proof.

## DESIGN_KEEP

Non-empty, for the same reason as `openpiton_pmesh_order`: the target's
instrument is registered. `T_MCIF_ORDER` reads `ref_count`, `ref_rd_ptr` and
`ref_mem` (through `expected_data`) and `ext_outstanding` (through
`outstanding_image`). Under `ENTER_FRA_KEEP` every register not matched by a
keep pattern starts arbitrary, so with an empty keep list the reference queue
starts arbitrary and `T_MCIF_ORDER` is falsified at cycle 0 for a reason that is
not the design's and that nothing in the design can correct.

The pattern in `taskdef.json` is

    u_checker\.(ext_outstanding|axi_pending|ref_wr_ptr|ref_rd_ptr|ref_count|seen_(req|ar|r|rsp))

matched unanchored against instance paths as `get_design_info -list register`
returns them. It is the checker instance and nothing else: the MCIF context
queue, the arbiter, the response FIFOs and the CVT/EG pipe flops all stay cut.

Three families, three reasons:

- `ext_outstanding`, `ref_wr_ptr`, `ref_rd_ptr`, `ref_count` — read by the
  target, directly or through `expected_data`/`outstanding_image`.
- `axi_pending` — read by the assumption `A_R_HAS_REQUEST`. Cut, the AXI return
  environment is stated against an arbitrary ledger, which is not the
  environment the task is stated in.
- `seen_req`, `seen_ar`, `seen_r`, `seen_rsp` — read by the four
  `C_ALL_CLIENT_*` covers and by nothing else. Cut, those four are reachable at
  cycle 0 for free and `COVER_DEPTH` measures nothing. They cost 16 bits.

`ref_mem` is deliberately NOT in the pattern, exactly as in pmesh. The checker's
reset branch assigns only the three pointer/count families; `ref_mem` is written
only on an accepted AXI beat, so it has no reset value at all, and `stopat
-reset` cuts a reset value. Keeping a register that has none is a no-op and
would only inflate the `KEEP_PATTERN design` count in the round log, which is
read as a measurement.

So the same caveat pmesh carries applies here and should travel with any result
from this task: "a read entry was written" holds by an argument, not by
construction. `response_owner_ok` requires `ref_count[t] != 0`, and a count only
becomes non-zero on the accepted beat that writes `ref_mem` at `ref_wr_ptr`, so
an entry is never read before it is written — **provided the pointers start at
reset**, which is what the keep set buys. The arbitrary initial contents of
`ref_mem` (4 x 64 x 512 = 131072 bits) are unobservable only because the pointer
state is anchored.

All kept families are reset-assigned, so the pattern cannot match zero and
cannot trip `cex.tcl`'s "design keep pattern matched nothing" FAIL.

The formal top holds no register at all — every declaration in
`ft/nvdla_mcif_order_ft.sv` is a `wire` — so there is nothing on the FT side to
keep or to cut.

## Dropped hash gates

The source's `DERIVATION.json` was NOT copied. It is a SHA-256 manifest — a
`source_sha256`/`destination_sha256` pair per file, and per-RAM-cell hashes in
the RAM-model locator — and this repo does not carry content hashes or
hash-based validation gates. Everything from it that is not a hash is recorded
above: the top, the target, the 12 assumptions, the 7 covers, the parameters,
the upstream file provenance and the derivation notes. The source file remains
in the source tree if the manifest is ever wanted.

## The v4 target-label blocker no longer applies

The two tasks ported on 2026-08-12 recorded a blocker: `v5/round.py` emitted
`set target_labels` from `v4pre_round.TARGETS`, the hardcoded the internal reference task pair,
so a ported task resolved no target and `cex.tcl` aborted with `no target
property resolved`. That has since been fixed — `v5/round.py:287` now reads
`taskdefs.TASKS[self.task]["target_labels"]`, and this package supplies that
key through `taskdef.json`. `v4pre_round.TARGETS` still holds the internal reference task
pair, which is correct for the v4 path and does not reach v5.

`cex.tcl:LABEL_INDEX` keys on the last dot-separated component of a property
name, so the bare label in `target_labels` is the right form.
