# opentitan_tlul_socket_order provenance

assembled: 2026-08-19

source: an earlier internal task package
        (copied out of; the source tree was not modified)

A single host drives symbolic TL-UL requests into the real OpenTitan
`tlul_socket_1n` (N=4, every direction FIFO at depth 4, all pass-through
enabled), four task-authored in-order responders sit on the device side, and an
independent 64-entry reference queue in the formal top asserts that the host
sees its responses back in request order, with the right `d_source` and the
right `d_data`. The socket, both TL-UL FIFO directions and every prim cell they
need are upstream lowRISC OpenTitan; the four responders, the reference queue
and the formal top are task-authored.

top: testbench
environment: lists/diag_tlul_socket_order.tcl  (task `diag_tlul_socket_order`)
target: T_TLUL_SOCKET_RESPONSE_ORDER  (testbench.T_TLUL_SOCKET_RESPONSE_ORDER)

The package ships its own environment: `testbench.A_RESET_IDLE` (no request
while reset is held) and `testbench.A_REQUEST_STICKY` (a stalled request holds
its device select, source, address and data until accepted). Both are written
in `ft/tb.sv`, so they are in the elaborated set before the diag runs and the
diag adds nothing to them.

The source `DERIVATION.json` also lists 5 covers -- `C_ALL_DEVICES`,
`C_HOST_BACKLOG`, `C_DEVICE_SWITCH_HOLD`, `C_RESPONSE_BACKPRESSURE`,
`C_REFERENCE_WRAP`. They elaborate with the package and are what `COVER_DEPTH`
will count if a round is given `--cover-s`. They are not targets.

Parameters, from `DERIVATION.json`: 4 devices, device model depth 4, host
request/response depth 4, per-device request/response depth 4, reference queue
depth 64.

## What changed from the source's tcl/setup.tcl, and why

The source's `fls_setup` is a single-shot evaluator for one frozen submission.

Kept: `clear -all`, `+define+SYNTHESIS`, `+incdir+rtl`, the 14-file analyze set
in the source's order, `elaborate -top testbench -disable_auto_bbox`,
`set_clock_reference_mode auto`, `clock clock`, `set_cumulative_reset on`,
`reset -expression {reset == 1'b1} -max_iterations 100`.

Dropped, with reasons:

- **The `FROZEN_INPUT_MISSING` existence check** over the sources plus
  `submission/helpers.sv`. It demands a submission file in the shape this
  harness does not use.
- **The name censuses** (`fls_require_exact_names` over `FLS_BASE_ASSERTIONS` +
  `FLS_HELPER_PROPERTIES`, and over the assumptions). They demand the
  elaborated property set equal a list computed by a Python front end that v5
  does not run. v5 stages a different helper set every round, so an exact-match
  census rejects every legal round. Not lost: `cex.tcl` runs `LABEL_INDEX`,
  `CHECK_FT_MODULES` and `CHECK_LABEL_COLLISIONS` after this file.
- **`TARGET_RESOLUTION_FAIL` / `HELPER_RESOLUTION_FAIL`.** Same reason. The
  target census survives in the diag as a printed count that fails only on zero.
- **`MULTI_DRIVEN` as an error.** Now reported as
  `MULTIPLE_DRIVEN count=... list=...`. An abort here kills the round before
  any verdict; the number in the log answers the same question.
- **`+define+FLS_EVALUATION` and `+incdir+$submission_dir`.** See the scrub
  below.
- **The whole of `tcl/evaluate.tcl`.** That is the source's own proofgrid
  policy and property ledger. v5 brings its own (`v5/grid.tcl`, `CONFIG_GRID`)
  and writes its own report. `tcl/` was not copied at all.

Added, not in the source: `AFRA_ELAB_EXTRA` handling (the payload exports it
unconditionally and a recipe that ignores it drops the run's elaborate switches
silently), `set_elab_time_limit`, `compilation -profile`, `task -create FPV`,
and the proofgrid profile load.

Deliberately NOT added: `-create_related_covers` / `-witness_cover_property`.
The source task elaborates without them, and they would attach
precondition/witness covers to every helper an agent writes, changing what the
cover phase counts.

`+define+SYNTHESIS` is load-bearing and was kept for that reason: it selects
`prim_assert_dummy_macros.svh` inside `prim_assert.sv`, which empties every
`ASSERT/`ASSUME embedded in the upstream socket, FIFO and counter RTL. Without
it the elaborated property set is a different task from the one stated here.

## Scrubbed

This package is copied into every agent workspace, so anything in it that
describes a solution or a golden environment would make the run not blind.

- `ft/tb.sv`, 3 lines deleted at the end of the module:

        `ifdef FLS_EVALUATION
        `include "helpers.sv"
        `endif

  Not a leak -- an incompatibility, and the same one recorded for
  `openpiton_pmesh_order`. In the source flow a submission is one `helpers.sv`
  textually included INSIDE the top module. v5 stages one bound standalone file
  per worker and `v5/elab.tcl` fails a worker whose file does not bind under
  its own module name. Left in, the directive is either inert (no
  `FLS_EVALUATION`) or fatal (no such file), and it would tell an agent to
  write in a shape the harness rejects. This is why `placement` for this task
  must be the standalone/`bind` one, which is what `taskdef.json` takes by
  default.

Nothing else was removed. In particular the source's `tcl/` and
`DERIVATION.json` were not copied (see below), and no comment in `rtl/` or
`ft/tb.sv` names a proof, a golden environment or a helper.

## Dropped hash gates

The source's `DERIVATION.json` was NOT copied. It is a SHA-256 manifest -- a
`source_sha256`/`destination_sha256` pair per file -- and this repo does not
carry content hashes or hash-based validation gates. Everything from it that is
not a hash is recorded above: the top, the target, the 5 covers, the
parameters, the upstream commit and the derivation notes.

## DESIGN_KEEP: pointers only, same shape as pmesh

`taskdef.json` carries

    "design_keep": ["ref_(write_pointer|read_pointer|count)"]

matched unanchored against instance paths as `get_design_info -list register`
returns them.

The target's instrument is registered. `ft/tb.sv` maintains a 64-entry
reference queue -- `ref_source`, `ref_data`, `ref_write_pointer`,
`ref_read_pointer`, `ref_count` -- and `T_TLUL_SOCKET_RESPONSE_ORDER` reads all
of it through `target_ok`. Under `ENTER_FRA_KEEP` every register not matched by
a keep pattern starts arbitrary. With an empty keep list the reference queue
starts arbitrary and the target is falsified at cycle 0 for a reason that is
not the design's and that no helper can correct.

`ref_source` and `ref_data` are deliberately NOT in the pattern, for the reason
recorded for pmesh: the reset branch assigns the two pointers and the count and
nothing else, so the two memories have no reset value at all and `stopat
-reset` cuts a reset value. Keeping a register that has none is a no-op, and it
would inflate the `KEEP_PATTERN design` count in the round log, which is read
as a measurement.

The same argument transfers with it, and a reader of a result needs it:
`target_ok` requires `ref_count != 0` before it reads
`ref_source[ref_read_pointer]`, and a count only becomes non-zero through a
host accept, which is the same event that writes both memories at
`ref_write_pointer`. So an entry is never read before it has been written --
**provided the pointers start at reset**, which is what the keep set buys. The
arbitrary initial contents of the two memories are unobservable by argument,
not by construction.

Left cut deliberately:

- `seen_devices`, `seen_hold`, `seen_wrap` -- cover-only state. An arbitrary
  start makes a cover easier to hit and cannot falsify the target.
- `past_valid` -- gates `A_REQUEST_STICKY` only. Arbitrary-1 makes the
  assumption fire one cycle early against arbitrary `$past` values, which
  constrains the environment more, never less.
- The four `ordered_tlul_device` responders (`source_mem`, `size_mem`,
  `data_mem`, `write_pointer`, `read_pointer`, `count`) and every register
  inside `tlul_socket_1n` and its six FIFOs. These are the design, and the
  invariants that relate them to the reference queue are exactly what a round
  is asking an agent to write.

The pattern matches at least the three named registers, so it cannot match zero
and cannot trip `cex.tcl`'s "design keep pattern matched nothing" FAIL. Expect
3 hits if Jasper lists these as scalars, which they are.

## Known caveat: `derive_targets` does not locate this target

The source writes the target as a LABELLED IMMEDIATE assertion inside an
`always_ff`:

    T_TLUL_SOCKET_RESPONSE_ORDER: assert (target_ok);

`taskdefs.TARGET_PATTERN` is the literal string `assert property`, so
`taskdefs.derive_targets("opentitan_tlul_socket_order")` returns
`{"source": "", "line": 0, "text": "not located in the mounted sources"}` and
`v5/model.py:target_text` prints that line into the model-phase prompt instead
of a file and line number.

Not fixed, on purpose. The fix inside this package would be to rewrite the
assertion as `assert property (...)`, which is a different property: a
concurrent assertion in procedural code is evaluated on sampled values in the
Observed region, and this is upstream-shaped task code that the source's own
Jasper flow signs off in its immediate form. Changing what the target MEANS to
make a prompt line prettier is the wrong trade. The label is correct in
`taskdef.json`, `cex.tcl` resolves targets by label out of its own index, and
the agent has `task/` and can find the line. Recorded here because a round log
for this task will show the "not located" text and it should not be read as a
broken package.

Both OpenTitan packages ported today have this shape; `openpiton_pmesh_deadlock`
and `openpiton_pmesh_waitcycle` do not.

## Not verified

and `reset_modes.tcl` are unexecuted. Slang and Jasper disagree about some
SystemVerilog and only Jasper's verdict admits a package to a round. The
register census and the `KEEP_PATTERN design` hit count are the smoke test.

## Known blocker, not fixable inside this package

The one recorded at the end of `tasks/openpiton_pmesh_order/PROVENANCE.md`
applies unchanged: `v5/round.py` emits the hardcoded `v4pre_round.TARGETS`
the internal reference task pair rather than `taskdefs.TASKS[task]["target_labels"]`, so a round
on this task resolves no target and `cex.tcl` aborts with `no target property
resolved`. The model phase is unaffected. The fix is one line in
`v5/round.py`, which a porting agent was told not to touch.
